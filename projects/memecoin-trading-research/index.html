No profitability is claimed. Simulated P&L was only printed to the console, and no trade ledger survives.

The idea

New Solana memecoins launch by the hundreds every hour. Most die within minutes, and a few spike hard in their first moments. The thesis was momentum at birth: if a token attracts serious money in its first trades, buy immediately, hold for at most two minutes, and exit on a tight take-profit or stop-loss. Speed matters, so the whole system is asynchronous Python polling several APIs at once.

Version 1 (Dec 2024): detect, then simulate

  1. Discovery. Poll the Rugcheck "new tokens" feed.
  2. Signal. For each new mint, pull its last five transfers from Helius and price them through DexScreener. If that early-buy volume exceeded $35k, raise an alert and log the token.
  3. Simulated trade. Open an equal-weight position (portfolio ÷ max positions) and monitor it every 2 seconds.

Version 2 (Sep 2025): safety first

The two versions bet on different payoff shapes. V1 let winners run to +20 % but cut losers at −5 %, needing roughly a one-in-five hit rate to break even. What the data shows

In about 4.5 hours the detector flagged 119 tokens. The distribution is bimodal. One cluster sits where real early buying should be (35ktoafew35k to a few 35ktoafew100k). A second cluster of roughly 50 tokens claims 30Mto30M to 30Mto1B in "early buys", which is impossible for coins minutes old. The likely cause is that transfer amounts were multiplied by price without scaling for each token's decimals. About 40 % of the signals were artifacts of a units bug, so the signal that decided entries was unreliable for nearly half of the tokens it fired on.

Why it stopped: tokens you can't sell

In live testing the failure wasn't bad entries. It was exits that couldn't happen. On Solana, a token's creator can keep a freeze authority (which can freeze any holder's token account) or set up delegate control. Some tokens the bot bought couldn't be sold. A strategy built on 120-second holds and tight stops is meaningless when the sell transaction can be blocked. So V2 put a safety check before every other filter and moved to devnet and simulation only.

The check itself had a bug. check_delegate_authority is passed the token's mint address but parses the bytes as an SPL token account (delegate flag at offset 72). A mint account is only 82 bytes, and its freeze_authority option sits at offset 46, so offset 72 lands inside the freeze-authority key. The function fails closed (any error or non-zero byte means skip), so it stayed conservative, but it wasn't testing what its name says. The correct design is:

Changes for next time

  • Check exits first. Liquidity, freeze authority and sell routes decide whether a strategy can run at all.
  • Check derived signals against physical limits. A token can't have $500M of buys in its first minute. Plotting the distribution would have caught the units bug immediately.
  • Save results. P&L that only goes to print() can't be analysed later. This project's results are only partially reconstructable for that reason.
  • Fail closed when a safety check errors. That part of the V2 check was correct.
